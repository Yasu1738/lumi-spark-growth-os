## 2. データの区別

| 区別 | 実装 |
|---|---|
| 実測値／サンプル | 全テーブルに `data_kind`（`real`／`sample`）。サンプル記事は `【サンプル】` で始まる |
| 確認済み事実／推定 | 記事の `verification_status`、`title_status`、`url_status`、`content_reviewed`、`notes` に推定の旨を記載 |
| 仮説 | `pre_hypothesis`、`hypothesis_verdict`（支持／部分支持／反証／未判定）。構造分析は「仮説」として表示し因果判定しない |
| 欠損と0 | 数値はNULL許容。空欄はNULL、`0` は計測結果0。表示は「未計測」と「0」で区別 |
| 記事別とアカウント全体 | `article_metrics` と `account_snapshots` を別テーブルに分離 |
| 24h／72h／累積 | `window_type`。24h・72hは公開時刻から18〜30時間／60〜84時間の範囲でのみ登録可。範囲外や公開時刻不明は累積として登録 |

| テーブル | 役割 | 主な列 |
|---|---|---|
| `articles` | 記事資産台帳 | 記事ID、タイトル（確認状態）、URL（確認状態）、公開日時、テーマ、主目的、想定読者、中心主張、タイトル構造／H／V／Cコード、導線段階、収益導線、関連タグ、本文確認済み、仮説、出典、確認状態、データ区分、旧台帳原文（legacy_json） |
| `hubs` | ハブ | ハブID、名称、ハブ記事、関連テーマ、状態 |
| `hub_path_steps` | ハブからの導線ステップ | 順番、ラベル、導線段階、割当記事 |
| `link_proposals` | 内部リンク提案 | リンク元／先、推薦理由、読者価値、リンク文、挿入場所、根拠、スコア、提案者、承認状態、関連性確認状態。UNIQUE(元,先)・CHECK(元≠先) |

## 4. リンク提案の状態遷移

```
提案 → 確認 → 承認 → note反映（人間が実施） → 表示確認
  └──────── 却下 ←──────┘（表示確認以外の段階から）  却下 → 提案（再開）
```

- 1段階ずつしか進めない。提案だけで公開済みにはならない。
- 「確認」時、両記事の本文確認済みフラグが立っていなければ関連性は「未確認（本文未確認の記事を含む）」のまま。
- 「承認」は承認者名が必須。さらに、両記事について「URLがオーナー提示または表示確認済み」「本文確認済み」「タイトル確認済み」「実データ」の条件を満たさない提案（仮案）は承認できない。
- すべての変更を `audit_log` に記録。

## 5. 構成

- 画面（`app/`）とデータモデル（`lumi_growth_os/`）を分離。画面はリポジトリ層の関数だけを呼ぶ。
- 推薦はタグ・テーマ・ハブ関連テーマ・導線段階の重み付けで計算（`recommend.WEIGHTS`）。LLM API不要。
- 将来の機能追加（LLM推薦、候補テーマ管理など）は `lumi_growth_os/` にモジュールを追加し、画面を `app/views/` に追加する。
